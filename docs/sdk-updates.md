# TikHub SDK 更新设计

本机首版已实现版本检测、独立启动器隔离安装、离线兼容性检查、API/worker 健康检查、切换与回退，并以故障模拟验证旧环境和锁文件恢复。真实新版本切换及 Linux 容器尚未实测；下文容器/CI 和完整线上响应兼容性流程仍为后续设计。当前能力以 [README](../README.md) 为准。

2026-10-20：离线兼容性检查已覆盖 TikTok、Twitter / X 与抖音实际使用的方法签名和脱敏 / 合成响应样例。抖音包括作者资料、`lite` 通道分页、视频详情与图集解析，检查不调用收费接口。

## 目标与权限

- 系统可以定期检测 TikHub SDK 更新，也支持管理员手动检查并触发“一键更新”。更新前显示当前版本、候选版本、发布说明、验证结果和预计重启范围。
- 只有 SuperHot 系统管理员可以更新或回滚。普通用户不能修改系统依赖、更新来源或执行命令。
- 所有用户共享同一套已部署的 SDK 版本；API、采集 worker 等使用 SDK 的进程必须部署一致的版本。
- 每个用户独立配置自己的 TikHub API Key。任务按所属用户取用凭据；SDK 更新不修改、覆盖或共享这些 Key。
- Key 不写入源码、镜像、依赖锁、构建产物、命令行参数或日志。运行日志和异常信息必须隐藏认证头及敏感字段。

## 正常集成不需要克隆 SDK 仓库

SuperHot 使用官方 PyPI 包 `tikhub`，并固定经过验证的版本和完整依赖锁。只有审阅源码、修复 SDK 或验证未发布提交时，才在独立开发目录克隆官方仓库；不把该仓库嵌入 SuperHot，也不通过定时 `git pull` 更新生产依赖。

固定允许的来源：

- GitHub 仓库：`TikHub/TikHub-API-Python-SDK`。
- PyPI 项目：`tikhub`，使用官方 PyPI 索引及其分发文件。

前端只提交后台已登记的目标版本或更新任务 ID，不能提交任意包名、下载 URL、Git 分支或 shell 命令。

## 版本检测

| 信息 | 获取方式 | 用途 |
| --- | --- | --- |
| 实际运行版本 | 各相关进程读取 `importlib.metadata.version("tikhub")` | 确认当前部署及多进程版本一致性 |
| 官方正式发布 | GitHub Releases API，读取标签、发布说明及发布时间 | 发现候选版本，排除草稿和预发布 |
| 可安装软件包 | PyPI 指定版本 JSON API | 确认同版本文件、Python 要求、撤回状态和 SHA256 |
| 未发布源码变化 | 可选读取 GitHub commit 信息 | 仅展示源码变化，不触发安装 |

检测示例入口为 `GET https://api.github.com/repos/TikHub/TikHub-API-Python-SDK/releases/latest` 和 `GET https://pypi.org/pypi/tikhub/<version>/json`。规范化 `v` 前缀并按版本规则比较，不能以字符串顺序或提交时间判断版本高低。普通更新不允许降级；降级使用独立的回滚流程。

GitHub 发布与 PyPI 上传可能不同步：发现 release 但同版本包尚未可用时，显示“等待软件包发布”，不能改装 `main`。初始可每 6 小时检查一次，缓存结果并支持手动刷新；检查失败时显示失败时间及上次成功结果，不能显示为“已是最新”。

## 更新执行流程

业务进程仅创建经过权限校验的更新任务。独立部署执行器运行预先定义的构建和部署步骤，记录操作者、目标版本、依赖差异、验证结果、源码修订、镜像摘要或环境标识。

1. **预检与锁定：** 限制同一部署只能执行一个更新任务；再次确认官方候选版本、PyPI 文件、SHA256、未撤回状态及目标 Python/操作系统兼容性。
2. **生成新依赖锁：** 在独立构建工作区修改版本声明并重新解析依赖，保存 `pyproject.toml` 与锁文件的配套修订。使用 uv 时，精确版本声明也须同步修改，再生成新 `uv.lock`；使用 pip 时，生成包含直接和间接依赖版本及哈希的锁定清单。禁止只修改数据库中的版本号或只升级已安装包。
3. **隔离构建与验证：** 在候选环境或新镜像内安装锁定依赖，校验包版本和依赖一致性；验证导入、SuperHot 已使用方法的签名及响应适配，执行用户解析、作品列表和更新去重等关键路径冒烟。真实接口验证在运行阶段使用独立测试凭据，凭据不进入构建；未完成真实验证必须明确标记，不能宣称线上兼容性已验证。
4. **暂停派发：** 验证通过后暂停新的采集任务，等待在途任务完成；超时任务按幂等规则恢复或重试。避免新旧 worker 同时处理同一任务，并确保只有一个有效调度器。
5. **切换并重启：** 部署新环境或镜像，统一重启使用 SDK 的进程，核对实际版本、健康状态与关键任务，再恢复派发。界面提示这是一次可能短暂中断采集的部署操作。
6. **失败处理与回滚：** 切换前失败则保留原运行版本；切换后健康检查失败则暂停新任务，恢复上一套环境或镜像及其锁定修订，核对版本后恢复调度。保留旧部署产物，不能临时重新解析旧版本依赖来代替回滚。

依赖声明和锁文件的更新必须作为 SuperHot 的可追溯发布修订保存，并与实际部署产物对应。更新成功后不能留下“线上新版本、仓库锁文件仍是旧版本”的状态。

## Windows 本机与 Linux 容器

| 部署方式 | 执行方式 | 回滚方式 |
| --- | --- | --- |
| Windows 本机 | 独立本地部署服务或受控脚本，在新的版本化目录创建完整候选环境；使用明确的 Python 路径安装并验证。通过已配置的服务管理方式停止相关进程、切换启动目录/环境并重启，不在正在运行的 `SuperHot` conda 环境内直接升级。 | 保留旧环境和启动配置，切回旧环境后重启。 |
| Linux 容器 | 独立执行器或 CI 按新锁文件构建并测试镜像，记录镜像 digest；部署器暂停派发、排空任务后替换相关容器。依赖安装发生在构建阶段，不在运行容器内执行 `pip install -U`。 | 使用保存的旧镜像 digest 和部署配置重新创建容器。 |

Windows 执行器只授予工作目录和指定服务所需权限，不默认需要 Windows 管理员权限；服务控制若需要额外权限，应在部署时单独配置。Linux 业务容器不挂载 Docker socket，不拥有宿主机任意命令权限。部署凭据由执行器或 CI 持有，Web API 不暴露通用 shell 执行接口。

数据库、用户 Key 和已采集内容保存在部署环境之外的持久存储中。SDK 更新不混入数据库结构迁移，避免一次 SDK 回滚还需要恢复业务数据。

## 状态与自动阻止规则

检测状态：`检查中`、`已是最新`、`发现更新`、`等待软件包发布`、`检查失败`、`兼容性阻止`。部署状态：`排队中`、`隔离验证中`、`构建完成`、`等待在途任务`、`部署中`、`更新成功`、`更新失败`、`回滚中`、`已回滚`。检测失败和部署失败应分别记录，保留最近一次成功部署信息。

发现以下情况时，自动停止更新并保留当前版本：

- 主版本升级、删除 SuperHot 已使用的接口、必需参数或响应结构发生不兼容变化。
- 包被撤回、校验失败、Python 要求不满足、依赖无法解析或依赖声明与锁文件不一致。
- 必要验证失败，或发布信息与检查结果不足以确认兼容性。

自动检查不能证明所有上游行为兼容，也不能自动修复业务适配。被阻止的版本需要先审查、修改 SuperHot 的 TikHub 适配层并重新验证，再作为可部署候选；管理员按钮不能跳过这些检查直接强制升级。
