# SuperHot 监控模块设计

> 状态：首版本地监控流程已实现，真实 TikHub 接口及媒体尚未实测。本地使用 SQLite + 单 worker；PostgreSQL、多 worker 和数据库服务器时间协调属于待验证的部署设计。本文保留设计背景，实际能力以 [README](../README.md) 为准。
>
> 更新日期：2026-10-19。开发环境为原生 Windows，未来部署环境为 Linux。

2026-10-20 已扩展 Twitter / X 与抖音监控；平台适配、素材下载及升级说明见 [Twitter 接入文档](twitter-monitoring.md)、[抖音接入文档](douyin-monitoring.md)。下文保留首期 TikTok 设计背景，最新实测边界见 README 与对应接入文档。

## 1. 目标与范围

SuperHot 是面向内部团队的可扩展商业助手系统。本模块先实现 TikTok 作者更新监控，规模按几百名作者考虑。用户注册登录属于系统基础能力；年费会员与支付暂不开发。本文件只描述监控模块与用户、凭据的关系。

首期已经确认的范围：

- 用户粘贴 TikTok 作者主页链接或作品链接，系统识别作者，展示作者信息，待用户确认后添加监控。
- 每个监控作者独立设置检查间隔，例如每 1、2、3 小时检查一次。
- 首次检查建立历史基线，已有作品作为历史内容，不作为刚发现的新更新提醒。
- 支持暂停、恢复和手动检查，显示最近检查时间、下次计划时间及异常状态。
- 后台进程持续执行监控，关闭浏览器或退出网页不会停止任务。
- 用户可以下载接口实际提供的视频、图片到浏览器所在电脑，并复制作品文案。
- 每个用户使用自己的 TikHub API Key，任务、权限、额度和调用归属按用户隔离。

首期不开发音频下载、ASR 语音识别和 AIGC。复制文案指接口返回的作品描述文字，不包含视频语音转文字或画面文字识别。

## 2. 添加监控对象的流程

1. 接收并校验链接，区分作者主页链接和作品链接。短链接、分享链接的实际兼容范围以验证结果为准。
2. 通过统一 TikHub SDK 适配层解析作者，取得平台用户标识、用户名、昵称、头像等可用信息。
3. 展示“将监控此作者”的确认信息。作品链接的含义是定位作品作者，后续监控该作者发布的新作品。
4. 用户确认作者并设置间隔后，创建本人名下的监控记录，安排首次基线检查。
5. 首次基线成功后进入正常周期；失败时明确显示“基线未完成”，重试之前不宣称已开始可靠识别新内容。

作者身份以 TikTok 返回的用户标识为主，保存原始链接和当前用户名作为辅助信息，避免把可变化的用户名作为唯一身份依据。同一用户重复添加同一作者时返回已有监控，避免意外创建重复收费任务。

## 3. 基线、新内容与补查

### 首次基线

首次成功获取的可见作品登记为历史基线，并记录基线建立时间、作品 ID 和平台发布时间。首批返回数量受接口限制，建立基线不等于下载全部历史作品。

后续补查遇到基线之前的作品时，归入历史记录，不把此前未保存的旧作品误报为新作品。页面需要区分“平台发布时间”和“SuperHot 首次发现时间”。

### 后续增量检查

每轮从最新作品开始获取，按作品 ID 与已保存记录去重；不能仅比较列表第一条、单个最大作品 ID 或单个发布时间。置顶、重复分页、内容延迟返回、排序变化等情况需要在接口验证中覆盖。

若一页不足以覆盖两次成功检查之间的更新，应继续按接口返回游标翻页。按既有记录、发布时间重叠范围和接口分页状态共同判断是否补齐；具体停止条件要在固定 SDK 和真实响应样本验证后落实。

单轮分页量、重试次数和请求时间需要设置上限，以控制用户自己的 API 消耗。达到上限或中途失败时保留“待补查”状态，后续继续处理，不把未完成的补查显示为完整成功。具体分页额度在接口验证后确定。

### 暂停、恢复与手动检查

- 暂停后不再发起新的周期检查；已经开始的请求可能完成并产生费用，结果仍需正确保存。
- 恢复后安排一次检查，并按暂停前的成功记录补查，再继续正常周期。
- 手动检查进入同一执行流程，使用相同的凭据校验、锁和限流规则，不额外启动绕过调度器的请求。
- 暂停状态下的手动检查按一次性检查处理，不自动恢复周期。
- 同一对象正在检查时，重复手动触发合并为待处理状态，避免并发请求同一对象。

这些按钮的状态和下一次检查时间应立即反馈给前端；实际执行仍由后台 worker 完成。

## 4. 技术方案

首版选用：

| 部分 | 方案 |
| --- | --- |
| Python | 3.13 |
| 调度库 | APScheduler 3.11.3，使用 `AsyncIOScheduler` |
| 执行进程 | 独立、常驻的 asyncio worker |
| 持久化 | PostgreSQL 保存监控对象、调度状态、运行记录及作品元数据 |
| 平台访问 | 统一 TikHub 官方 Python SDK 适配层，拟固定 v2.2.0 并验证实际方法和参数 |
| 首期运行方式 | API 服务与监控 worker 分开启动，Windows 开发和 Linux 部署采用相同业务代码 |

首版不引入 Redis 和 Celery。几百名作者、小时级检查以受限并发的异步网络请求为主，当前方案能够减少基础设施数量；实际容量仍需以分页量、接口响应时间和每个 Key 的限制进行验证。

APScheduler 只负责一个固定周期的扫描任务，例如每 10～30 秒唤醒一次。该频率是后台扫描数据库的频率，不是调用每个作者 TikHub 接口的频率。作者只有在自己的 `next_check_at` 到期后才会被领取执行。

扫描任务本身使用内存 jobstore，worker 启动时重建。PostgreSQL 中的业务记录是每个作者调度状态的唯一来源，不再同时维护数百份持久化 APScheduler jobs。APScheduler 的扫描任务配置 `max_instances=1`、`coalesce=True`，并使用固定任务 ID；启动时立即补做一次数据库扫描。

worker 必须作为常驻进程运行。开发时可以在独立终端启动；部署时由 Linux 的进程管理机制负责开机启动、异常重启和日志。APScheduler 本身不是系统服务，关闭 worker 所在进程就会停止实际检查。

## 5. 调度状态、租约与重启恢复

建议至少保存以下业务字段，最终字段名可随数据库设计调整：

| 信息 | 示例字段 |
| --- | --- |
| 所属关系 | `owner_id`、`credential_id` |
| 平台身份 | `platform`、`author_id`、`sec_user_id`、`source_url` |
| 用户配置 | `enabled`、`interval_hours` |
| 计划与结果 | `next_check_at`、`last_attempt_at`、`last_success_at`、`last_error` |
| 基线和补查 | `baseline_at`、`baseline_status`、`backfill_needed` |
| 执行领取 | `lease_owner`、`lease_token`、`lease_expires_at` |
| 失败控制 | `failure_count`、重试时间及错误分类 |

执行顺序：

1. 用数据库时间查询已到期、未暂停且没有有效租约的记录。
2. 在短事务中原子领取任务并写入租约；可使用 `FOR UPDATE SKIP LOCKED`，领取后立即提交。
3. 在数据库事务之外调用 SDK，应用全局并发限制及每个用户 Key 的并发、频率限制。
4. 按作品唯一键保存结果和运行记录，仅由仍持有对应租约令牌的执行者完成状态更新。
5. 成功后推进下一次正常检查时间；失败后分类退避重试，保留最近成功位置和待补查状态。

不应在整个远程请求期间持有数据库行锁。请求超时、租约期限及必要的租约续期需要配套设置，避免慢请求尚未结束就被其他执行者重新领取。

worker 重启后立即扫描数据库，到期记录继续执行；崩溃遗留的租约到期后可以重新领取。停机期间错过的多个周期合并为一次当前检查，再通过作品分页补查内容，不为每个错过的小时重复请求同一份最新列表。

恢复与重试可能造成外部 TikHub 请求重复，无法承诺外部 API 恰好调用一次。内容保存必须幂等，例如对用户归属、平台、作者和作品 ID 建立合适的唯一约束；重复执行不得重复增加作品记录或重复生成同一条更新事件。

APScheduler 3.x 的 `max_instances` 只约束该 scheduler 内的任务实例，不能替代业务租约，也不能提供跨进程互斥。首版只启动一个监控 worker；API 的多个服务进程都不启动 scheduler。未来扩展多个 worker 时，应继续由数据库原子领取任务，并重新验证按 Key 限流的跨进程一致性。

## 6. 每用户 API Key 隔离

- 凭据必须属于当前任务的用户；执行时按 `owner_id` 与 `credential_id` 验证归属和启用状态。
- 后端保存加密凭据，前端只显示脱敏状态，不回显完整 Key。加密主密钥通过部署配置提供，不写入仓库。
- Key 不进入 URL、浏览器下载链接、普通日志、运行错误详情或 APScheduler 任务参数；扫描任务只处理业务记录 ID。
- 同一作者被不同用户监控时，各自任务使用各自 Key，分别记录调用归属和结果权限。首版不跨用户借用 Key，也不合并不同用户的请求来变更费用归属。
- 重复任务合并只发生在同一用户的同一作者内。用户之间的数据缓存与共享策略不作为首版的隐含优化。
- Key 失效、额度不足或被限流时，更新该用户对应任务的状态，避免无限重试；不能自动切换使用其他用户的 Key。

所有 TikHub 调用都经过统一 SDK 适配层，集中处理超时、响应校验、异常分类、重试和必要日志。业务代码不分散调用重复的 App/Web 接口，前端不直接调用 TikHub。

## 7. TikHub 最小接口链

以下为已经查到的官方文档能力，不是已完成的连通性测试。接口路径省略统一前缀 `https://api.tikhub.io/api/v1`；实际 SDK 方法名和字段路径要按固定版本验证。

| 场景 | 文档中的接口及参数 | 计划用途 |
| --- | --- | --- |
| 作者主页链接 | `GET /tiktok/web/get_sec_user_id`，`url` | 获取用于识别作者的 `sec_user_id` |
| 作者信息 | `GET /tiktok/app/v3/handler_user_profile`，`sec_user_id`、`user_id` 或 `unique_id` | 展示作者确认信息；优先使用已解析的 `sec_user_id` |
| 作品分享链接 | `GET /tiktok/app/v3/fetch_one_video_by_share_url`，`share_url` | 取得作品，再从作者信息归一到监控对象 |
| 正常作品轮询 | `GET /tiktok/app/v3/fetch_user_post_videos`，`sec_user_id`、`max_cursor=0`、`count=20`、`sort_type=0` | 获取最新作品；后续使用响应中的 `max_cursor` 翻页 |
| 已知作品详情 | `GET /tiktok/app/v3/fetch_one_video`，`aweme_id` | 在列表字段不足或用户下载时补取作品数据，是否必需取决于实际响应 |
| 候选备用列表 | `GET /tiktok/web/fetch_user_post`，`secUid`、`cursor`、`count` | 只有验证后才纳入受控降级策略，不把多接口同时请求作为默认行为 |

主页链接也可以先提取标准 `@用户名`，再用用户信息接口解析；短链接等形式需另行验证。作品返回结构中的作者 ID、图集字段、视频地址和文案字段都要保存代表性测试样本，不能只凭接口名称推断完整支持。

官方资料：

- [提取 TikTok 用户 sec_user_id](https://docs.tikhub.io/186826077e0)
- [获取 TikTok 指定用户信息](https://docs.tikhub.io/186826106e0)
- [根据 TikTok 分享链接获取单个作品](https://docs.tikhub.io/186826105e0)
- [获取 TikTok 用户主页作品 V1](https://docs.tikhub.io/186826108e0)
- [TikHub TikTok 接口概览，含已知作品详情入口](https://tikhub.io/tiktok-api)
- [TikTok Web 用户作品列表](https://docs.tikhub.io/186826058e0)
- [TikHub Python SDK v2.2.0](https://github.com/TikHub/TikHub-API-Python-SDK/releases/tag/v2.2.0)

Web 用户作品列表文档明确说明每页最多 15 条、按时间倒序，使用 `cursor` 与 `hasMore` 翻页，而且相邻页面可能出现重复作品。App V3 的分页、排序与实际响应仍需单独验证，不能照搬 Web 的字段和限制。

SDK v2.2.0 是客户端版本，不等于 TikHub 上游接口、TikTok 平台行为或媒体地址已经稳定。

## 8. 视频、图片和文案

下载目标是用户浏览器所在电脑。用户在网页点击下载后，由浏览器完成文件保存；后台只按需获取或代理媒体流，不把所有监控内容自动归档到服务器磁盘。

若媒体地址需要 Cookie、特定请求头或存在跨域限制，由后端受控下载接口处理。该接口通过当前用户有权访问的作品记录获取媒体地址，不接受任意远程 URL，不向浏览器暴露 TikHub Key。媒体链接失效时，可用用户自己的 Key 重新获取作品数据，相关请求应记入该用户运行记录。

作品列表能返回媒体字段，不代表其中每个地址都能直接下载。TikHub Web 文档说明部分视频 CDN 地址需要返回的 `tt_chain_token`；特定播放链接又要求不携带 Cookie。这些规则需要在适配层按已验证响应处理，不能统一对所有链接附加相同请求头。

首版只展示并下载实际可取得的视频或图片。私人、删除、地区受限等不可用内容以及媒体类型识别失败应返回明确状态，不把空结果当作已经下载成功。图集、视频、多媒体混合内容的具体支持范围要通过真实样本验证后确认。

复制文案使用已保存的作品描述文字；浏览器剪贴板失败时提供可选中的文字。接口没有提供的完整文案不能凭空补齐。

## 9. 时间、状态与可观测性

数据库时间使用 UTC，时间字段采用带时区类型；租约到期、任务领取和下次检查都基于数据库时间，减少不同进程时钟和时区设置造成的差异。

前端按用户当地时区展示，当前团队可默认使用 `Asia/Shanghai`。平台发布时间、发现时间、最近检查时间、最近成功时间和下次检查时间分别显示其含义，不混用。

需要记录每次检查是否成功、返回作品数、新增作品数、分页量、耗时、失败类别和脱敏请求标识。对用户展示可理解的异常，例如“Key 无效”“额度不足”“接口限流”“内容不可用”“待补查”，避免直接暴露第三方原始响应中的凭据和内部信息。

## 10. 实现前的验证与验收

已在原生 Windows 的 `SuperHot-dev` Conda 环境安装 Python 3.13.16、TikHub 2.2.0 和 APScheduler 3.11.3，并通过依赖一致性、客户端导入和 asyncio 定时任务的离线检查，具体环境见 [README](../README.md)。尚未使用 API Key 调用付费接口，真实 TikTok 响应与媒体下载仍未实测。下一步先以少量代表性作者验证调用链，再确定默认并发、分页上限和重试策略。

核心验收场景：

- 主页链接、作品长链接和常见分享短链接能定位正确作者，并由用户确认。
- 首次历史作品不报为新内容，下一轮新增作品只入库一次。
- 作者作品多于单页、存在置顶或跨页重复时，能够去重并显示补查完成程度。
- 两个用户监控同一作者时，凭据、执行记录、费用归属和可见结果保持各自隔离。
- 暂停、恢复、手动检查和修改间隔不会产生同一对象的并发重复任务。
- 关闭浏览器后仍能检查；worker 被终止、重启后恢复到期任务，崩溃租约可到期回收。
- Key 失效、额度不足、限流和接口异常不会形成密集重试。
- 代表性视频、图片能保存到浏览器所在电脑；不可用媒体有明确反馈；文案可复制。
- Windows 开发和 Linux 部署使用相同 worker 逻辑，UTC 存储与当地时间展示一致。

## 11. 调度方案的官方依据

- [APScheduler PyPI](https://pypi.org/project/APScheduler/)：本次核对的稳定版为 3.11.3，要求 Python ≥3.8，列出的 Python 版本包含 3.13；库支持跨平台，但本身不是守护进程或系统服务。选择 Python 3.13 仍需验证完整依赖组合。
- [APScheduler 3.x AsyncIOScheduler](https://apscheduler.readthedocs.io/en/3.x/modules/schedulers/asyncio.html)：支持 asyncio 事件循环和原生协程任务。
- [APScheduler 3.x FAQ](https://apscheduler.readthedocs.io/en/3.x/faq.html)：多个进程共享同一持久化 jobstore 会引发重复或漏执行；推荐独立调度进程。
- [APScheduler 3.x 用户指南](https://apscheduler.readthedocs.io/en/3.x/userguide.html)：说明 `max_instances`、错过执行时间、`misfire_grace_time`、`coalesce`，以及持久化任务初始化时的固定 ID 与 `replace_existing=True`。本文用业务数据库恢复作者任务，不依赖持久化 jobstore 自动恢复每个作者。
- [PostgreSQL SELECT 锁定规则](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)：`SKIP LOCKED` 可用于多个消费者访问队列表；它只解决领取时的数据库锁竞争，后续执行仍需租约和幂等设计。
- [Celery 官方 Windows 支持说明](https://docs.celeryq.dev/en/stable/faq.html#windows)：从 Celery 4.x 起不再正式支持 Windows，因此不作为原生 Windows 开发的首版默认任务执行方案。

以上官方行为约束与本文的具体业务设计是两个层次；单进程、数据库租约、补查合并和按 Key 隔离是针对 SuperHot 首期规模作出的设计选择，仍需通过实现和验收验证。
